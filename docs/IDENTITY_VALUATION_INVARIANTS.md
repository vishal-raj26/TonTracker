# Identity Valuation Invariants

These rules apply to TON DNS and Telegram Username collectibles. They define
what may be displayed, what may enter a portfolio total, and what must be
prepared before a wallet import.

## Evidence and display

1. Only finalized, public, native-GRAM sales with a sale-time USD conversion
   may train a model, populate an exact-history valuation, or produce a market
   baseline.
2. Listings, bids, transfers, social claims, private chats, copied sessions,
   and private-group information are not sale evidence.
3. A route, length, spelling, or structural match may locate candidate data,
   but it cannot by itself establish a portfolio value for a textual identity.
4. A prepared archetype baseline is an `indicative` value. It can make a first
   import informative immediately, but it is low confidence and excluded from
   totals.

## Portfolio eligibility

1. One finalized exact sale is visible as low-confidence evidence only.
2. At least two finalized exact sales are required before an identity estimate
   can be portfolio eligible.
3. The estimate must also be current, medium/high confidence, and generated by
   the active estimator version.
4. A verified active listing is a market signal, not a portfolio valuation.

## First-import contract

1. Wallet import performs bounded D1 reads by NFT address and canonical name.
2. If no prepared exact value exists, it uses a versioned compact baseline and
   may enqueue a background alias refresh. It never crawls marketplaces in the
   request path.
3. Precomputed baselines and exact values refresh independently of wallet
   imports. Wallet-size growth does not make valuation discovery slower.

## Current versions

- TON DNS: `dns-market-v7`
- Telegram Username: `username-market-v16`

Any estimator change that alters confidence or comparable eligibility must
bump the corresponding version and rebuild the compact D1 projection before
the application serves it.
